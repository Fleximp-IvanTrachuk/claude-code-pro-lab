# Промпты для spec-kit

Готовые тексты для команд spec-kit. Порядок работы с каждой фичей:
`/speckit.specify` → `/speckit.clarify` → `/speckit.plan` → `/speckit.tasks` → `/speckit.analyze` → `/speckit.implement`.
Конституция (`/speckit.constitution`) создаётся один раз в начале.

Каждая фича = отдельная ветка spec-kit (`NNN-name`) = отдельный Pull Request (домашка).

---

## Целевая архитектура

Проект состоит из двух хранилищ с разными ролями:

- **Мастерская — DuckLake.** Сюда приходят файлы, здесь их очищают, нормализуют и маппят.
  Всё «грязное» и спорное живёт только здесь.
- **Витрина — StarRocks.** Сюда публикуются только полностью очищенные и замапленные данные:
  факты и мастер-данные. Отсюда строят дашборды в self-service BI.

```
Excel ──▶ inbox ──▶ ETL (Python, Polars) ──▶ raw ──▶ normalized ──▶ aggregates (для маппинга)
                                                        ▲                  │
                                                        │                  ▼
                                               справочники ◀── UI маппинга (Streamlit) ◀── data steward
                                                        │
                    publish: только готовые периоды ────┴──▶ Parquet ──▶ StarRocks ──▶ Superset ──▶ дашборды

Docker: Postgres (каталог DuckLake), UI маппинга, StarRocks, Superset
```

### Роли и user stories

| Роль | User story |
|---|---|
| Data engineer | Подключаю нового дистрибьютора одним YAML-конфигом и получаю отчёт о загрузке и об изменениях структуры файла. |
| Data steward | Вижу нераспознанные продукты, области и клиентов, отсортированные по объёму продаж, и сопоставляю их со справочником в веб-интерфейсе — начиная с тех, что дают основной объём. |
| Data steward | Вижу, какая доля объёма каждого дистрибьютора за период уже замаплена, и публикую готовый период в витрину. |
| Аналитик / менеджер | Сам строю дашборды по продажам и остаткам (SKU, области, дистрибьюторы, покрытие аптек) без помощи разработчика. |

### Слои мастерской (DuckLake)

Слой называется по тому, что произошло с данными:

| Слой | Что лежит | Где |
|---|---|---|
| `raw` (сырые) | Содержимое каждого входного Excel как есть, без изменений; один Parquet на файл. Только дописывается, никогда не правится — из него можно пересобрать следующие слои | `data/lake/raw/` (Parquet-файлы) |
| `normalized` (приведённые) | Единая схема: SKU, коды областей, количество в упаковках. Таблицы `fact_sell_in`, `fact_stock`, справочники, `unmapped`, `load_log`, `structure_snapshots` | схема `normalized` в DuckLake |
| `aggregates` (агрегаты) | Служебные агрегаты для маппинга: незамапленные значения по объёму, доля замапленного объёма по дистрибьютору и периоду, готовность периода к публикации | схема `aggregates` в DuckLake |

Каталог DuckLake: на этапе 1 — файл `data/lake/catalog.ducklake`; с этапа 2 — Postgres в Docker
(файл допускает только одного пишущего, а ETL и UI маппинга пишут одновременно).
Данные таблиц — Parquet в `data/lake/tables/`.

### Витрина (StarRocks)

Звёздная схема: факты продаж и остатков + измерения (продукты/SKU, области, дистрибьюторы, клиенты, календарь).
Бизнес-агрегаты для дашбордов — здесь, а не в мастерской.

## 1. `/speckit.constitution`

```
Проект: Distributor ETL — учебный pet-проект для курса по Claude Code и для изучения
Python, Polars, Parquet, DuckDB, DuckLake, Docker, StarRocks и self-service BI.
Параметрический ETL принимает Excel-файлы фармдистрибьюторов (sell-in и stock),
приводит их к единой схеме в мастерской на DuckLake, где данные очищаются и маппятся
через веб-интерфейс. Полностью очищенные факты и мастер-данные публикуются в витрину
StarRocks, к которой подключается self-service BI для дашбордов.

Принципы:

I. Конфиг вместо кода. Новый дистрибьютор подключается только YAML-конфигом
   (pydantic-валидация). Код не содержит имён конкретных дистрибьюторов, листов
   или заголовков.

II. Устойчивость к дрейфу структуры. Лист ищется по набору колонок, строка шапки —
   по максимуму совпадений, колонки — через синонимы (рус/укр, без учёта регистра,
   пробелов и пунктуации). Пропала обязательная колонка — понятная ошибка; необязательная —
   предупреждение; лишняя — запись в лог.

III. Ничего не теряется молча. Нераспознанные области, продукты и клиенты попадают в
   карантин (`unmapped`), отклонённые строки считаются и попадают в `load_log`.

IV. Мастерская и витрина разделены.
   Мастерская — DuckLake: raw (сырой Parquet по каждому входному файлу, только
   дописывается) → normalized (единая схема, справочники, карантин) → aggregates
   (служебные агрегаты для маппинга: незамапленное по объёму, готовность периодов).
   Слой normalized всегда можно пересобрать из raw.
   Витрина — StarRocks: звёздная схема из фактов и мастер-данных, бизнес-агрегаты.
   Обработка — Polars (lazy API, где уместно), SQL — DuckDB в мастерской, StarRocks в витрине.

V. В витрину — только чистое. Период дистрибьютора публикуется в StarRocks только
   после того, как доля замапленного объёма достигла порога готовности и стюард
   подтвердил публикацию. Незамапленный остаток в витрину не попадает.
   Публикация идемпотентна: повторная публикация периода заменяет его данные.

VI. Идемпотентность и аудит. Повторная загрузка того же дистрибьютора за тот же
   период заменяет данные в одной транзакции. Каждая загрузка — снапшот DuckLake,
   который фиксируется в `load_log`; отпечатки структуры — в `structure_snapshots`.

VII. Тесты сначала. pytest; для каждой фичи — тесты на обезличенных файлах,
   включая реальные исторические изменения структуры (переименован лист, колонки,
   заголовки, язык областей).

VIII. Реальные данные — только локально, в репозиторий — только обезличенные.
   Исходные файлы дистрибьюторов лежат в `data/private/` (в .gitignore) и никогда
   не коммитятся. Скрипт `scripts/anonymize.py` делает из них обезличенные копии
   в `data/samples/`:
   - заменяет названия дистрибьюторов (в ячейках, именах файлов и листов),
     клиентов, адресов, названия и коды продуктов на псевдонимы
     (`Distributor A`, `Клиент 0001`, `Продукт 001`); одно и то же реальное значение
     во всех файлах получает один и тот же псевдоним;
   - искажает количества (секретный коэффициент + шум), сохраняя целочисленность,
     знак и согласованность итоговых строк;
   - сохраняет структуру без изменений: листы, заголовки, порядок колонок, лишние
     строки сверху, итоги, исторические версии файлов, язык названий областей.
   Таблица соответствий «реальное → псевдоним» и коэффициенты хранятся только в
   `data/private/`. Обезличенные файлы попадают в git только после ручной проверки.

IX. Воспроизводимое окружение. Все сервисы (Postgres, UI маппинга, StarRocks,
   Superset) описаны в `docker compose` и поднимаются одной командой. Конфигурация —
   в git, данные — в volume или в папках, исключённых из git. Сервисы добавляются
   по одному, по мере этапов.

X. Обучение — часть результата. Каждая фича содержит `docs/learning/NNN-*.md`:
   какие возможности инструментов использованы, почему, и небольшой пример для
   самостоятельного запуска. Предпочитать понятное решение хитрому.

Технологические ограничения:
- Этап 1 (ETL): Python 3.12, uv, Polars, fastexcel (calamine) для чтения Excel,
  openpyxl для записи обезличенных копий с сохранением структуры, pydantic v2,
  DuckDB + расширение ducklake, typer для CLI, pytest, ruff.
- Этапы 2–5: Docker Desktop + docker compose, Postgres (каталог DuckLake),
  Streamlit (UI маппинга), StarRocks (витрина), Apache Superset (self-service BI).
Всё работает локально: `data/lake/` (raw/, tables/, catalog.ducklake),
`data/inbox/`, `data/archive/`, `data/private/` — в .gitignore.

Процесс: одна фича spec-kit = одна ветка = один Pull Request. Ветка main —
первая сдача. В PR — ссылка на spec.md, plan.md и learning-заметку.
```

## 3. `/speckit.specify` для фичи 001

```
Первая сдача Distributor ETL: каркас проекта и сквозной путь
«Excel → raw (Parquet) → normalized (DuckLake)» в мастерской на DuckLake.

Что нужно:
- Скрипт обезличивания scripts/anonymize.py: берёт реальные файлы дистрибьюторов
  из data/private/ (не в git) и создаёт копии в data/samples/. Названия
  дистрибьюторов, клиентов, адресов и продуктов заменяются на устойчивые псевдонимы,
  количества искажаются, а структура файла (листы, заголовки, лишние строки, итоги,
  исторические версии) остаётся как в оригинале. Таблица соответствий хранится только
  в data/private/. Повторный запуск даёт те же псевдонимы.
- Дальнейшая работа ведётся только на обезличенных файлах из data/samples/.
- YAML-конфиг на каждого дистрибьютора; на этом этапе лист и строка шапки указаны
  в конфиге явно.
- Содержимое каждого входного файла без изменений сохраняется в слой raw как Parquet.
- Парсер читает файл по конфигу, приводит к единой схеме sell-in / stock
  (типы, количество в упаковках), отбрасывает пустые и итоговые строки.
- Нормализованные данные загружаются в слой normalized (DuckLake) в таблицы
  fact_sell_in и fact_stock. Каталог DuckLake — файл data/lake/catalog.ducklake.
- Исходный файл после загрузки переносится в data/archive/.
- README: как поставить окружение, обезличить данные, запустить загрузку и
  посмотреть результат в DuckDB.

Пользователь — data engineer, который кладёт файлы в data/inbox/ и хочет увидеть их в
единых таблицах. Справочники, автопоиск, дрейф, идемпотентность, слой aggregates,
UI маппинга и витрина StarRocks — вне рамок этой фичи (следующие домашки).
```

## Открытые вопросы

Из брифа (ответить на `/speckit.clarify` фичи 001):

- Гранулярность периода: месяц / неделя / день.
- Есть ли у sell-in номер и дата документа отгрузки или только период.
- Дата остатка: на конец периода или на дату файла.

К следующим этапам:

- Маппинг клиентов (одна аптека у разных дистрибьюторов) — входит в фичу 012 целиком или только справочник, а сопоставление позже.
- Порог готовности периода к публикации: 100% замапленного объёма или допустимый остаток (например, 99%).
- Superset или Metabase — окончательно решить на фиче 015.
